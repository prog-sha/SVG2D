# Godot GDExtensionのクロスビルド

対象Godotで読み込める拡張ライブラリを、必要なOS・CPU・debug/releaseの組み合わせで生成する。既存のビルド設定と検証スクリプトを優先し、コンパイル成功と実行確認を区別する。

## 最初に確認するもの

- 作業ツリーの変更、`SConstruct`、`.gdextension`、`godot-cpp`のリビジョン、API指定、`build_profile`、既存のビルド・テスト・CI手順を読む。
- 対象一覧は依頼と`.gdextension`の`[libraries]`から作る。`entry_symbol`、`compatibility_minimum`、precision、CPU、Webのthreads、iOS実機／simulator、依存ライブラリも照合する。ファイル名や対応対象を推測で増やさない。
- インストール済みのコンパイラ・SDK・コンテナを調べる。バージョンやオプションは採用中の`godot-cpp/tools/`と公式資料で確認する。ライブラリの版をビルド都合で更新しない。

環境別のコマンドと注意点は [platforms.md](references/platforms.md) を必要な対象だけ読む。SVG2Dをビルドする場合は [svg2d.md](references/svg2d.md) から既存の入口へ進む。他のプロジェクトへSVG2Dの名前・パス・対象数を持ち込まない。

## ビルドの進め方

1. ホスト用の短いビルドでAPI・ヘッダー・リンクの問題を解決してから、他の対象へ展開する。
2. 同じ作業ディレクトリのSConsは順番に実行する。`godot-cpp/gen`、文書の生成ソース、`.sconsign.dblite`を複数プロセスで書き換えない。並列化するなら同じ入力から作った独立ディレクトリ・コンテナを使い、各ビルド内で`-j`を指定する。
3. API・precision・build_profileなど生成コードの構成が変わったら、影響する生成物・オブジェクト・静的ライブラリを既存のclean手順で揃える。構成の違うヘッダーと古いライブラリを組み合わせない。
4. ビルド開始時の入力を固定し、対象ごとにコマンド・ツールチェーン・ログ・成果物を記録する。途中でソースを直した場合は、その修正が影響する対象を再ビルドする。
5. 一時成果物とログはプロジェクトの`tmp/`へ置く。コンテナは今回作ったものを名前で管理し、そのコンテナだけ停止・削除する。完成した配布物だけ既存の出力先へ戻す。

## 差分ビルド

既存のキャッシュがあれば判定対象を確認して使う。コンパイラ・SDK・NDK・コンテナイメージを変更した場合、それらが入力指紋に含まれない仕組みでは影響する対象を強制的に再ビルドする。新たに判定を用意する場合は、ソース、ビルド定義、godot-cppの版と変更、生成設定、ツールチェーン、対象オプション、出力ハッシュを対象ごとに比較する。中間オブジェクトやログをソース指紋に含めない。文書がdebugだけに入る構成なら、その差も分ける。

「既存出力を現在の入力として登録する」操作はビルドではない。同じ入力から作ったことが確認できる成果物にだけ使う。欠損、破損、出所不明の出力を登録してビルドを省略しない。無変更の再実行で必要な対象だけが省略されることを確認する。

## 検証と完了

- `.gdextension`の各対象が実在する出力へ解決し、形式・CPU・debug/release・必要な依存関係が一致することを確認する。名前を変更しただけの別CPU成果物を受け入れない。
- ホストでは既存のヘッドレス／CLIテストで拡張の読み込みと公開APIを確認する。エディタ機能は必要な統合テスト、SIMD変更は通常計算との比較を使う。
- クロス成果物は最低限ヘッダー・シンボル・依存関係を確認し、利用可能な実機・エミュレータ・ブラウザでは読み込みも確かめる。静的検査だけの対象を「動作確認済み」と報告しない。
- 配布先・検証済みの範囲・未検証の範囲を簡潔に伝える。コミットやプッシュは依頼の範囲にある場合だけ行い、既存のユーザー変更を混ぜない。

公式の仕様確認には [godot-cpp](https://github.com/godotengine/godot-cpp)、[公式テンプレート](https://github.com/godotengine/godot-cpp-template)、[.gdextensionの仕様](https://docs.godotengine.org/en/4.7/engine_details/engine_api/gdextension/gdextension_file.html) を使う。ローカルの採用版と資料の版が異なるときは、採用版の実装・設定を先に確認する。
